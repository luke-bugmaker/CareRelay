CareRelay - how to run it, and how to wipe the demo data
=========================================================
Last updated: 2026-07-26
Last verified running: 2026-07-26, Azure AI Foundry gpt-5-mini (section 0b)

All paths below are relative to this folder (CareRelay/).
You need TWO terminals: one for the backend, one for the frontend.


-----------------------------------------------------------------
SHORTCUT - DOUBLE-CLICK CareRelay.bat INSTEAD
-----------------------------------------------------------------

CareRelay.bat sits in this folder and does the typing for you:

    [1]  Start CareRelay      - sets up the Python environment and
                                the npm packages on first run, opens
                                both windows, waits for the API, says
                                whether real AI is connected, opens
                                the browser.
    [2]  Reset the demo data  - stops the backend, deletes the
                                database and the uploaded photos, and
                                puts the browser command for the chat
                                bubbles on your clipboard.
    [0]  Exit

Option 2 is also how you delete tasks: the UI has no delete button
for them, so wiping the database is the way to clear the schedule.

The rest of this file is the same work done by hand, plus every
setting the launcher does not cover.


-----------------------------------------------------------------
0. FIRST TIME ONLY - PYTHON ENV AND API KEY
-----------------------------------------------------------------

    cd backend
    python -m venv .venv
    .\.venv\Scripts\python.exe -m pip install -r requirements.txt

Then put your AI key in the .env file in this folder (CareRelay\.env):

    AI_API_KEY=sk-...
    AI_BASE_URL=https://api.openai.com/v1
    AI_MODEL=gpt-4o-mini

.env is gitignored. It is never committed and never pushed to GitHub.
If .env is missing, copy .env.example to .env and edit that.

Any OpenAI-compatible provider works - only BASE_URL and MODEL change:

    OpenAI      https://api.openai.com/v1                          gpt-4o-mini
    Foundry     https://<resource>.services.ai.azure.com/openai/v1 <deployment name>
    DeepSeek    https://api.deepseek.com/v1                        deepseek-chat
    Qwen        https://dashscope.aliyuncs.com/compatible-mode/v1  qwen-plus
    Moonshot    https://api.moonshot.cn/v1                         moonshot-v1-8k
    OpenRouter  https://openrouter.ai/api/v1                       <vendor>/<model>
    Ollama      http://localhost:11434/v1                          qwen2.5

Leaving AI_API_KEY empty is allowed. The app still starts, it just uses a
small offline keyword parser instead of real AI.


-----------------------------------------------------------------
0b. IF YOUR KEY IS FROM AZURE AI FOUNDRY
-----------------------------------------------------------------

This is the setup this project was last tested on, so it gets its own
section. No Azure CLI, no "az login", no azure-identity package - the
plain API key is all you need.

In the Foundry portal:

    Deployments -> click your model -> Playground -> "Call model" tab

Copy the two boxes on that panel:

    Project endpoint  ->  goes in AI_BASE_URL
    API Key           ->  goes in AI_API_KEY   (click the eye icon to reveal)

Ignore the Python sample underneath them. Its "Authentication method"
dropdown defaults to "Entra ID authentication", which needs az login.
Switch nothing - CareRelay uses key authentication against the exact
same endpoint.

Resulting .env:

    AI_API_KEY=<the API Key you copied>
    AI_BASE_URL=https://<your-resource>.services.ai.azure.com/openai/v1
    AI_MODEL=gpt-5-mini

(<your-resource> is whatever the Project endpoint box showed. The real
values for this machine are already in CareRelay\.env, which is
gitignored - these two files are public, so they keep placeholders.)

Two ways this goes wrong:

  * The endpoint MUST end in /openai/v1. Drop that suffix and every
    call comes back 404.
  * AI_MODEL is the DEPLOYMENT name shown in the Deployments list, not
    the model name from the catalogue. They usually match, but if you
    renamed the deployment, the deployment name wins.

Speed: gpt-5-mini is a reasoning model, so it thinks before answering.
Measured on 2026-07-26: 6-13 seconds per chat message, about 35 seconds
for a handoff summary over a busy day. Slow is expected here, not broken.

Cost note: a workshop / lab Foundry resource can be deleted or run out
of quota once the workshop ends. If everything suddenly returns 401 or
404 having worked before, check the deployment still exists in the portal.


-----------------------------------------------------------------
1. START THE BACKEND  (terminal 1)
-----------------------------------------------------------------

    cd backend
    .\.venv\Scripts\python.exe -m uvicorn app.main:app --reload

Leave it running. Stop it with Ctrl+C.

Check it worked - open http://localhost:8000/health
You should see:

    {"status":"ok","ai_configured":true,"ai_model":"gpt-5-mini"}

  "ai_configured": true   -> real AI
  "ai_configured": false  -> NOT the real AI. The app silently falls
                             back to a small keyword parser and still
                             looks like it works. See section 5.

Settings are read once at startup, so restart uvicorn after editing .env.


-----------------------------------------------------------------
2. START THE FRONTEND  (terminal 2)
-----------------------------------------------------------------

    cd frontend
    npm run dev

Then open:  http://localhost:5173

First time only, run "npm install" before "npm run dev" (about 15 seconds).

Look at the badge in the top-right corner of the page:

    "Live backend"  -> talking to FastAPI + real AI       <- what you want
    "Demo data"     -> backend not reachable, using fake
                       in-browser data instead

If it says "Demo data" while the backend IS running, the backend probably
crashed - look at terminal 1.


-----------------------------------------------------------------
3. CLEAN THE CHAT HISTORY
-----------------------------------------------------------------

There are TWO separate places data is stored. Clearing one does not clear
the other. For a totally fresh demo, do both.

CareRelay.bat option 2 does 3b for you and hands you 3a on the
clipboard. What follows is the manual version.

--- 3a. The chat bubbles on screen (stored in your browser) ---

Each caregiver has their own chat thread, saved in the browser's
localStorage so it survives a page refresh.

In the browser, press F12 to open DevTools, click "Console", paste this
and press Enter:

    localStorage.removeItem('careRelay.threads');
    localStorage.removeItem('careRelay.caregiverId');
    location.reload();

The chats are now empty and you are asked to pick a caregiver again.

Quick alternative: open the page in a private / incognito window. Nothing
is kept there at all.

--- 3b. The care events, tasks and photos (stored in the backend) ---

This is the timeline, the upcoming tasks and any uploaded photos.

  1. Stop the backend in terminal 1 (Ctrl+C).
     You MUST stop it first - Windows will not delete a file that a
     running program still has open.

  2. Delete the database and the uploaded files:

         cd backend
         del care_relay.db
         del /q uploads\*.png uploads\*.jpg

     (Do not delete uploads\.gitkeep - git needs it.)

  3. Start the backend again (section 1).

It re-creates the database automatically and re-seeds the demo data:
Amy and Ben, one breakfast event at 08:30, and one physiotherapy
appointment tomorrow at 15:00. That physio slot is what the demo's
schedule-conflict step clashes with, so do not delete it by hand.

IMPORTANT for the demo: seeding only happens when the database has no
caregivers in it. Keep yesterday's care_relay.db and you keep yesterday's
timestamps - the seeded physio is then "today at 15:00", not "tomorrow",
and step 3 of the demo produces no conflict card. Delete the database on
the morning of a demo.


-----------------------------------------------------------------
4. THE 2-MINUTE DEMO
-----------------------------------------------------------------

  1. Chat tab, pick Amy.
  2. "Dad ate half a bowl of porridge at 8:30."
     -> an "AI understood" card appears. Press Confirm.
  3. "Dad has physiotherapy tomorrow at 3 PM."
     -> Confirm. The clash with the seeded 15:00 physio shows up here,
        AFTER you press Confirm, not before.
  4. Care Board tab -> your events are on the timeline.
  5. Press "Generate handoff to Ben".
  6. Click a small "source" chip in the summary -> it jumps to the
     original entry. Hover it to see the caregiver's exact sentence.

Chinese input works too:  爸爸中午喝了一杯水，看起来比平常累。

Note: whether "Dad took his medicine." triggers the "Which medication?"
question depends on the model you configure. Smaller/faster models often
record it straight away instead of asking.

Live AI takes a few seconds per message. That is normal, not a hang.


-----------------------------------------------------------------
5. IF SOMETHING IS WRONG
-----------------------------------------------------------------

"npm is not recognized"
    Node.js is not installed, or the terminal is older than the install.
    Open a new terminal.

Port 5173 already in use
    npm run dev -- --port 5174

Port 8000 already in use
    An old backend is still running. Close that terminal, or:
    Windows: netstat -ano | findstr :8000     then stop that PID.

Page is blank
    Press F12, open Console, read the first red error.

Badge says "Demo data" and will not change
    The backend is not answering. Check http://localhost:8000/health.

health says "ai_configured": false
    CareRelay\.env is missing, or AI_API_KEY / AI_MODEL is blank.
    Copy .env.example to .env, fill it in, restart uvicorn.
    This file is deliberately NOT in git, so a fresh clone will not
    have it.

Backend log shows 401 / "invalid api key"
    The key does not belong to the provider in AI_BASE_URL. Both must
    come from the same provider. An Azure Foundry key against
    api.openai.com is the usual version of this mistake.

Backend log shows 404 / "model not found"
    AI_MODEL is not a model that provider serves. Check their model list.
    On Azure Foundry, also check AI_BASE_URL still ends in /openai/v1 and
    that AI_MODEL is the deployment name.

Backend log shows 400 "Unsupported parameter: 'max_tokens'"
    A reasoning model (gpt-5*, o-series) refuses that older parameter and
    wants max_completion_tokens. llm_client.warmup() already tries the new
    name first and falls back, so this should only show up in code you add.

Chat works but every message takes 10+ seconds
    Normal on a reasoning model. Point AI_MODEL at a non-reasoning model
    (gpt-4o-mini, deepseek-chat) if you want snappier demo answers.

Step 3 of the demo shows no conflict card
    The database is older than today. See section 3b.

Photo does not appear on the Care Board
    Uploading needs the backend running. In "Demo data" mode the photo
    only lives in the browser and disappears on refresh.

Everything looks stale after editing code
    Frontend reloads by itself; hard-refresh with Ctrl+Shift+R.
    Backend only reloads if you started it with --reload.


-----------------------------------------------------------------
6. WATCHING COST
-----------------------------------------------------------------

Usage and spend live in your provider's own dashboard (OpenAI platform
usage page, DeepSeek console, DashScope console, Azure Foundry's Monitor
tab, and so on). CareRelay sends one request per chat message and one
per handoff.

Never commit the key. CareRelay\.env is gitignored for exactly this
reason - do not move the key into .env.example, README.md or any file
that is tracked. If a key ever does reach a screenshot or a commit,
regenerate it in the provider's portal rather than deleting the file.
